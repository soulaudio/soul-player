SOUL PLAYER SEEK IMPLEMENTATION ANALYSIS
========================================

EXECUTIVE SUMMARY
-----------------
Soul Player's seek implementation contains ~230 lines of unnecessary complexity that don't improve user experience. Most production music players (Spotify, Apple Music, VLC) use simpler approaches.

KEY OVERCOMPLICATIONS IDENTIFIED
---------------------------------

1. PROGRESS INTERPOLATION (128 lines)
   - What: Runs 60fps RAF loop to smooth progress bar between backend updates
   - Problem solved: Progress bar jumps every 100ms instead of smoothly advancing
   - Reality: Spotify and Apple Music don't interpolate. Users don't notice/care
   - Impact: Zero UX benefit for 128 lines of code + RAF overhead
   - Recommendation: REMOVE

2. IGNORE WINDOW (15 lines of logic + 2 refs)
   - What: Ignores backend position updates for 120ms after seek
   - Problem solved: Prevents progress bar from jumping backward due to stale updates
   - Reality: Fragile band-aid. Hardcoded 120ms is arbitrary. Doesn't work on slow networks
   - Better solution: Just use optimistic update. Let backend overwrite it
   - Recommendation: REMOVE

3. SEEKING FEEDBACK SPINNER (20 lines)
   - What: Shows loading spinner for 120ms after seek
   - Problem: 120ms timer doesn't match actual backend completion time
   - Result: Spinner disappears before seek completes, or stays after completion
   - Better solution: Either remove entirely (optimistic update is enough) or listen to actual completion
   - Recommendation: REMOVE

4. MULTIPLE STATE FLAGS (30+ lines)
   - What: isDragging, isHovering, isSeeking (three separate booleans)
   - Problem: States are mutually exclusive. Should be single enum
   - Rendering: Three separate conditional blocks for three handle states
   - Better solution: Use single enum: 'idle' | 'dragging' | 'seeking'
   - Recommendation: REFACTOR (save 50 lines)

5. 100ms POSITION UPDATE INTERVAL (10+ lines in calculation)
   - What: Backend calculates position update threshold from sample count
   - Problem: 100ms is arbitrary precision. More updates = more network traffic
   - Reality: Spotify uses 100-200ms, Apple uses 200-500ms. No difference to users
   - Better solution: Simple 500ms timer. 5x less traffic, simpler code
   - Recommendation: OPTIONAL (lower priority)

WHAT'S GOOD (KEEP)
------------------
1. Optimistic UI updates - Instant feedback when user seeks
2. Drag-to-seek preview - Shows destination before commit
3. Clamping to prevent EOF - Prevents error states

COMPLEXITY BY THE NUMBERS
--------------------------
Current:
  - 370+ lines of seek-related code
  - 3+ state variables for UI states
  - 2+ refs for timing
  - 1 RAF loop during playback
  - 5+ async operations per seek

After simplification:
  - ~150 lines (60% reduction)
  - 1 state variable
  - 0 refs
  - 0 RAF loops
  - 2 async operations per seek

IMPLEMENTATION ROADMAP
----------------------
Phase 1 (Safe, Low Risk) - 60 minutes total
  1. Remove interpolation (30 min) - Delete useInterpolatedProgress.ts
  2. Remove spinner (20 min) - Remove isSeeking state and spinner rendering
  3. Remove ignore window (10 min) - Simplify seek command

Phase 2 (Refactoring) - 45 minutes
  4. Simplify state (45 min) - Combine boolean flags to single enum

Phase 3 (Optional) - 30 minutes
  5. Reduce update interval (30 min) - Use 500ms timer instead of 100ms

Total effort: ~105 minutes to save ~278 lines
Result: Simpler codebase, better performance, same UX
